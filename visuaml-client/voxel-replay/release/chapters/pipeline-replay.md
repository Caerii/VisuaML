# Find the first difference in a model and tool pipeline

Install the CPU PyTorch dependency as in the quickstart, then install
the pipeline extra from the repository root.

```sh
python -m pip install '.[pipeline]'
cd visuaml-client/voxel-replay
python release/examples/pipeline/run_pipeline.py /tmp/visuaml-pipeline
visuaml-replay compare-pipelines /tmp/visuaml-pipeline/reference.jsonl \
  /tmp/visuaml-pipeline/handoff.jsonl --output /tmp/handoff-result.json
```

Load the comparison JSON in the replay viewer. In CI, add
`--fail-on-difference` to exit 1 on a mismatch. The default writes
the diagnostic successfully, including when the two runs disagree.

| Intervention | First comparable boundary | Reference | Candidate |
| --- | --- | --- | --- |
| Change the model's weight buffer | Tool request | Argument 4 | Argument 5 |
| Change the guest's addition | WASM result | 7 | 9 |
| Change the delivered feedback | Model feedback | 7 | 0 |

The same model sees the reference tool return 7 on both sides of the
handoff intervention. After substitution it sees 0 and its decision
flips. The host explicitly makes the request and delivers the feedback.
The [saved results](../examples/pipeline/results.json) include model and
guest hashes, ordered observations, and the size and digest of each tool
report. The changed guest's [runnable report](../examples/pipeline/guest-tool-report.json)
can be opened with `visuaml-replay open` or examined with `inspect`.
The other reports and model files are generated by the example.

## Compare across model runtimes

```sh
visuaml-replay compare-onnx /tmp/visuaml-pipeline/reference.pt2 \
  /tmp/visuaml-pipeline/model.onnx /tmp/visuaml-pipeline/bindings.json \
  /tmp/visuaml-pipeline/value.npy /tmp/visuaml-pipeline/feedback.npy
```

The binding file maps the PyTorch tensor outputs, in order, to logical
observation names and ONNX output names. The ONNX graph can have different
internal operators. A fused intermediate can participate if it is exposed
as a graph output. The result carries shapes, dtypes, digests and the first
differing tensor element, with optional explicit floating-point tolerances.
The demo exercises trusted CPU artifacts.

## Integrate an existing harness

Use `visuaml.replay.pipeline.observation(request, boundary, value, runtime=...)`
to turn a selected value into one JSONL row. Compare iterators of rows with
`compare_observations`. Record stable logical request and boundary identifiers.
Worker completion order can differ across runs, so merge or compare separate
request streams in a common logical order. Runtime names describe provenance.
Missing rows and unexpected ordering are reported at the first disagreement.
The comparator stops reading once it has enough evidence to identify it.

Observations support finite JSON, with a 4,096-byte value limit. For large
tensors, `tensor_identity` records shape, dtype and a logical-order content
digest. Use selected numeric slices or named output comparison when
tolerances matter. Keep model files and large inputs in your existing
artifact store and include their identities in your harness manifest.
The comparison report carries the first differing values. A WASM report
is a separate artifact and embeds its full 64 KiB memory page. Review
both before sharing. The JSONL interface works across processes, and the
current implementation assumes ordering supplied by the harness.

## Bring a Rust tool as compiled

Both shipped WASM variants export immutable `__heap_base` and `__data_end`.
The loader admits those declarations and reports their values. The guest
instructions cannot access globals in this profile. Unsupported opcode
diagnostics include a function number and byte offset within its body.
The original binaries run with the existing tensor graph and are compared
with Wasmtime for return and full memory.

```sh
visuaml-replay describe release/examples/pipeline/tool.wasm
```

Rebuild both with Rust 1.100.0 using the flags below. Build the second with
`--cfg changed_tool` and name its output `changed-tool.wasm`.

```sh
rustc release/examples/pipeline/tool.rs --crate-type=cdylib \
  --target=wasm32-unknown-unknown -C opt-level=z -C panic=abort \
  -C link-arg=-zstack-size=0 -C link-arg=--global-base=1024 \
  -C link-arg=--initial-memory=65536 -C link-arg=--max-memory=65536 \
  -C link-arg=--export=__heap_base -C link-arg=--export=__data_end \
  -o /tmp/tool.wasm
```

## Measure journal scale

```sh
PYTHONPATH=../backend python tools/benchmark_pipeline_stream.py
```

The local test reads two JSONL files with 100,000 rows each. The final row
is different. About 15.8 MB of input produces a 337-byte comparison in
0.99 seconds. Python allocations traced during a separate repeat peak
at about 44 kB, close to the same test at 1,000 rows. This measures the
comparator on ordered journals. It excludes model serving, storage
transport, and cross-worker merge costs. [Raw samples](../examples/pipeline/stream-timings.json)
